- =playlist-remove <index>= — drop a specific entry
- =playlist-clear= — everything except the currently played file

- =--idle=yes= (plus your =loop-file=1= background) keeps mpv alive when the queue empties; without it mpv quits at the end of the playlist.

/Concepts you'll encounter/

- /Derive macro/ — a procedural macro invoked as =#[derive(...)]= that generates trait impls for your type. =EnumString= and =Display= here are derives supplied by =strum_macros=, not by =std=. This is why the string mapping can be declared once and have both =Display= and =FromStr= generated from it.

- /=FromStr=/ — the std trait =fn from_str(s: &str) -> Result<Self, Self::Err>=. =#[derive(EnumString)]= implements it, so you can call ="main".parse::<Role>()?=. Parsing is case-sensitive by default; the crate offers =#[strum(ascii_case_insensitive)]= to relax it.

- /=Display=/ — the std trait for ={}=-formatting. =#[derive(Display)]= implements it so =format!("{role}")= yields the variant's string.

- /Attributes/ — =#[strum(...)]= on the enum or on individual variants, e.g. =serialize = "..."= (parsing direction) and =to_string = "..."= (formatting direction). Yes, but not for the reason you'd expect. Memory is not the problem. An entry is a URL plus a small options list, call it a few hundred bytes; five-minute fragments over a week is about 2000 entries, roughly half a megabyte. "Overflow" in the sense of exhausting memory is not a real risk.

- *Index arithmetic.* If your Rust-side =VecDeque= is the source of truth, mpv's indices drift relative to it as entries accumulate. Pruning at the head keeps the two aligned, which is the argument I should have made instead of inventing auto-pruning.
- *O(n) enumeration.* Anything that walks the playlist — a Lua script, an observer on the =playlist= property, a debug dump — gets slower forever.
- *Round-trip cost.* =playlist-remove= per entry is a separate command. Pruning 500 entries is 500 IPC round trips; do it once per interaction, not per frame.

** =cycle pause = is the canonical toggle

#+begin_src rust
fn toggle_pause(&self) -> Result<()> {
    self.command("cycle", &["pause"])
        .context("Pause toggle failed")?;
    Ok(())
}
#+end_src

=cycle= is an input command like any other, so it is reachable identically from =input.conf=, from JSON IPC, and from =libmpv= — that equivalence is the point of the command interface, which exists so that "a number of ways to interact with the player" (key bindings, OSD, JSON IPC, client API) all drive the same command set [rksvc.github.io](https://rksvc.github.io/mpv-manual/command-interface/). The mplayer-compat bindings file shows the same verb in use for booleans: =m cycle mute= [github.com](https://github.com/mpv-player/mpv/blob/master/etc/mplayer-input.conf).

* The two non-toggle spellings

/Explicit, when you know the desired state:/

#+begin_src rust
self.set_property("pause", true)?;   // libmpv2 property setter
#+end_src

Over IPC this is the =set_property= form, as in the =pauseallmpv= script that pauses every running instance at once [git.wessel.gg](https://git.wessel.gg/dotfiles/.local/raw/branch/main/bin/pauseallmpv). Prefer it when your Rust state machine already knows whether it wants paused or playing — it is idempotent, whereas =cycle= is not.

/Via =command()= with =set=/ (mpv ≥ 0.38, supersedes =set_property=):

#+begin_src rust
self.command("set", &["pause", "yes"])?;
#+end_src

The =set= command is listed among the playback-control commands in the current command list [rksvc.github.io](https://rksvc.github.io/mpv-manual/command-interface/list-of-input-commands/). Check it exists on your deployment build before relying on it; =cycle pause= has no such version gate.

* Caveats

- /Do not read-then-write./ =let p: bool = get_property("pause"); set_property("pause", !p)= races against any other client — your web handler, input.conf, a Lua script, or the =pauseallmpv=-style sweep. =cycle pause= performs the toggle atomically inside mpv, which is why it is the right primitive for a button that any number of visitors can hammer.
- /=cycle= takes an optional direction:/ =cycle pause up= / =cycle pause down=. Absent a direction on a boolean property, it toggles. Not needed for your case.
- /=--keep-open=yes= produces a paused-at-EOF state/ that is indistinguishable from a user pause via the =pause= property alone. If your UI needs to tell "visitor paused the video" from "fragment finished, waiting", track that in your own state rather than inferring it from =pause=. This is the same ambiguity that made remote-control questions like ["is it possible to programmatically pause a video launched with mpv"](https://stackoverflow.com/questions/35013075/pause-programmatically-video-player-mpv) less trivial than they first appear — the IPC socket answer works, but knowing /why/ playback stopped requires more.
- /Return type./ =Mpv::command= gives you =Result<()>=; a bare =.ok()= in your current =tokio::spawn= block is fine for the fire-and-forget background load, but for a copy-paste =todo!()= replacement you want the error propagated or at least logged, not dropped.
