You are right about the cursor. You are wrong about two things: what =append-play= does, and what =clear_playlist= does. And the "extra clips" question has a clean answer that falls out of the first.

*=append-play= does not interrupt*

mpv's =loadfile= flags: =append= appends; =append-play= appends /and plays only if nothing is currently playing/. With a transition on screen, "nothing is playing" is false, so =append-play= degrades to =append=. The comment in your code — "just start playing the new clips immediately" — assumes a =replace=-style semantics that =append-play= simply doesn't have. So in the Transition branch, the new intro is /appended behind the current transition/, not started.

*=clear_playlist= erases the entry you just appended*

=playlist-clear= is documented as "clear the playlist, except the currently played file." The intro you just appended via =append-play= is not the currently playing file — it's the last entry — so the very next command deletes it. Net effect of your Transition branch:

#+begin_src 
[start]    playlist is [.. current_transition ..]
append-play intro2          → [.. current_transition, intro2, main2, outro2 ..]
playlist-clear              → [current_transition]           # intro2 is gone
append main2, outro2        → [current_transition, main2, outro2]
#+end_src

The new fragment's intro is silently dropped, and the fragment's first /observable/ clip is =main2= — which by then is a Main clip, so the next press takes the Main branch again. That's the mechanism by which "it works, mostly, but the queue keeps growing."

*Where the extra clips come from*

Not from failed commands. From =next()= having single-step semantics while =append= is unbounded, combined with a media-title race.

=playlist-next= advances the playlist cursor by exactly one entry. Your Main branch does two things per press: appends 3 entries at the tail, then advances the cursor once. If the cursor is currently on =main1=, one =next()= lands you on =outro1=. Fine for one press.

Now mash button 2 three times before =outro1= has actually started. The property read =media-title= still returns ="Main"= (it's the tag force-set on the still-current entry; the property does not flip to ="Transition"= until =outro1= has actually begun playing and its own =force-media-title= has taken effect). So all three presses evaluate the =Some(VideoType::Main)= arm:

#+begin_src 
press 1: append [i2,m2,o2]; next() → o1
press 2: append [i2,m2,o2]; next() → ???
press 3: append [i2,m2,o2]; next() → ???
#+end_src

The playlist is now =[.., m1, o1, i2, m2, o2, i2, m2, o2, i2, m2, o2]= and the three =next()= calls have each moved the cursor one entry. Depending on timing they land on =o1=, then =i2=, then =m2=, leaving the playlist with two unused copies of =[i2, m2, o2]= still queued ahead of whatever you press next.

This is the exact mechanism you were looking for: *=append= grows the tail by 3 per press; =next()= shrinks the remaining distance by 1 per press.* Nothing in the Main branch ever removes the tail. *How to fix it*

The discussion thread for "add to playlist while media is currently playing" is the same pattern from a user perspective ([github.com](https://github.com/mpv-player/mpv/discussions/14702)).

enum PlayMethod {
    Immediately,  // insert-next-play: start it now if nothing else is; else insert after current
    Queue,        // insert-next:      line up after current, no jumping
}

fn send_play_command(&self, path, is_loop, video_type, method) -> Result<()> {
    self.command(
        "loadfile",
        &[
            path,
            match method {
                PlayMethod::Immediately => "insert-next-play",
                PlayMethod::Queue       => "insert-next",
            },
            "0",
            &format!("loop-file={},{}",
                if is_loop { "inf" } else { "no" },
                video_type.tag()),
        ],
    )?;
    Ok(())
}
#+end_src

#+begin_src rust
Some(VideoType::Main) | None => {
    // Current entry is main (or nothing). Slot the new fragment immediately
    // after it, in reverse so that insertion order yields intro→main→outro.
    let mut q = queue;              // [intro?, main, outro?]
    while let Some((path, looping, vt)) = q.pop() {
        self.send_play_command(path, looping, vt, PlayMethod::Queue)?;
    }
    self.ensure_not_paused()?;
    // No next() — insert-next already guarantees this fragment is what plays next.
}

Some(VideoType::Transition) => {
    // We are mid-transition and want to abort it in favour of the new intro.
    // insert-next-play doesn't abort; use replace for the first clip.
    let ((path, looping, vt), rest) = queue.split_first()
        .ok_or_else(|| anyhow::anyhow!("empty clip queue"))?;
    self.send_play_command(path, *looping, *vt, PlayMethod::Immediately)?; // see below
    for (path, looping, vt) in rest {
        self.send_play_command(path, *looping, *vt, PlayMethod::Queue)?;
    }
}
#+end_src

One caveat for the Transition branch: =insert-next-play= still /inserts/, it doesn't abort. If you genuinely want the new fragment's intro to replace what is on screen right now, you need =loadfile <path> replace= (drop the =clear_playlist= call entirely — replace already discards everything except the new file, and you then =insert-next= the remaining two). But be aware that "replace on every subsequent press" is exactly the interruptive behaviour you originally used =append-play= to avoid — if a press arrives /while the new fragment's own intro is still playing/, =main=-branch semantics will kick in (intro is a Transition), and you'll take the Transition branch again, replacing the intro you just started with a fresh copy of itself. That is fine functionally, but you may want a short debounce. The app-level fix — coalescing pending commands in a =tokio::sync::watch= so the worker only ever sees the most recent =Play= — still applies and is cheaper than debouncing in mpv.

*Summary of what was actually wrong*

1. =next()= is one-step; =append= is per-fragment. Multiple presses accumulate fragments but only advance the cursor once each. Remaining entries play in FIFO order.
2. =append-play= is not =replace=. It does not interrupt a currently playing file.
3. =playlist-clear= preserves only the currently playing entry, so the entry you just appended in the Transition branch is immediately deleted — the fragment's intro is silently lost, which is why subsequent presses look like Main-branch presses.
4. =media-title= is a property of the currently playing file; while the cursor is moving, it still reports the OLD file's tag. The Main branch therefore handles several rapid presses even after the first =next()= should have moved the cursor onto a Transition clip.

Fix is =insert-next= / =insert-next-play= for slotting, and =replace= for the Transition branch's genuine interrupt; drop the explicit =next()= entirely. Then add the app-level "latest press wins" coalescing so mashing doesn't queue N copies of the same fragment in the first place.
